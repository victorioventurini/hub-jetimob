## 📋 Resumo das Correções

### 1. Função Duplicada `cleanup_old_logs()` ✅

**Problema:** Existiam duas versões da função com o mesmo nome:
- `cleanup_old_logs()` — sem parâmetros (legada)
- `cleanup_old_logs(p_agent_logs_days, p_perf_days, p_cron_days, p_wizard_days)` — com parâmetros

**Correção:** Removida a versão sem parâmetros. Agora existe apenas a versão parametrizada.

**Uso correto:**
```sql
-- Executar cleanup com valores padrão (14, 14, 7, 30 dias)
SELECT * FROM cleanup_old_logs(14, 14, 7, 30);
```

---

### 2. INSERT Policy Faltante em `audit_logs` ✅

**Problema:** A tabela `audit_logs` tinha apenas SELECT policy, causando falha em INSERT de reports de problemas (`ReportProblemDialog`).

**Erro observado:** `NO_BU_CONTEXT: User is not authenticated`

**Correção:** Adicionada policy:
```sql
CREATE POLICY "audit_logs_insert_authenticated" ON public.audit_logs
FOR INSERT TO authenticated
WITH CHECK (true);
```

## ⚠️ Warnings de Segurança (Intencionais)

Os warnings sobre `WITH CHECK (true)` em `app_error_logs` e `audit_logs` são **by design**:
- Essas tabelas são logs de sistema
- INSERT precisa funcionar mesmo antes do contexto BU estar disponível
- Usuários autenticados podem inserir logs livremente
- SELECT é protegido por policies específicas
